# QuotaBar Repository Contract

## Purpose

QuotaBar is a native macOS menu bar utility that reports account-based Codex
and ZCode subscription usage. Preserve account scope, privacy, and truthful
coverage labels; never replace provider-account totals with device-local logs.

Read `README.md`, `Docs/PRODUCT.md`, and `Docs/ARCHITECTURE.md` before changing
behavior or structure.

## Layout and Ownership

- `project.yml` is the authoritative Xcode project specification.
- `QuotaBar.xcodeproj` is generated by XcodeGen. Never hand-edit its project
  file.
- `Sources/QuotaBar/` owns application code.
- `Tests/QuotaBarTests/` owns unit and integration tests.
- `Docs/PRODUCT.md` owns product behavior and acceptance criteria.
- `Docs/ARCHITECTURE.md` owns durable component boundaries and data semantics.

Keep the application dependency-light. Prefer Apple frameworks and SQLite3.
Do not add a package dependency without documenting why the standard library
or platform SDK is insufficient.

## Validation

- Regenerate the project after changing `project.yml`: `xcodegen generate`.
- Full validation: `prek run --all-files && prek run --hook-stage pre-push --all-files`.
- Targeted validation: `prek run <hook-id> --files <paths>` when the selected
  hook supports file-level scope; otherwise run that hook across all files.
- Build only:
  `xcodebuild -project QuotaBar.xcodeproj -scheme QuotaBar -configuration Debug -derivedDataPath .build/DerivedData CODE_SIGNING_ALLOWED=NO build`.
- Documentation-only validation: `prek run --files <changed-document-paths>`.

Run the narrowest relevant test while iterating and full validation before a
handoff. Do not claim a GUI behavior was verified from compilation alone.

## Security and Privacy

- Read usage metadata only. Never persist prompts, responses, repository paths,
  browser cookies, tool output, or raw credentials.
- Never print authorization tokens or credential values in logs, diagnostics,
  test fixtures, or error messages.
- Keep ZCode credential access behind a dedicated interface with explicit
  error states and redacted diagnostics.
- Treat provider protocols as fallible. Preserve the last successful snapshot
  with a stale timestamp rather than inventing zero usage.

## Git and Publication

The base branch is `main`. Use a short-lived branch named
`<prefix>/<lowercase-hyphenated-topic>` for substantial or concurrent work;
trivial approved maintenance may be applied directly to `main`. Use a sibling
worktree and a PR for issue-bound, public, or independently reviewed work.

Allowed commit subjects use `prefix: concise imperative summary` with no scope
and no trailing period:

- `feat`: user-visible functionality.
- `fix`: correctness repairs.
- `docs`: documentation only.
- `refactor`: behavior-preserving structure.
- `test`: tests only.
- `build`: project generation, dependencies, or packaging.
- `ci`: continuous-integration configuration.
- `chore`: other maintenance.
- `revert`: a prior change reversal.

Commits, branches, publication, PRs, tags, releases, deployment, and cleanup
require their own user authorization. The publication target is the public
GitHub repository `zydtiger/QuotaBar`; do not publish elsewhere or change its
visibility without approval. The repository currently distributes source only:
no tags, binary releases, signing, notarization, or deployment are configured.
A future release requires a separately approved versioning and distribution
contract.

Maintain one writer at a time. Preserve unrelated user changes and never use a
destructive Git command to discard work.
